1. WHAT THE PRODUCT IS
----------------------
Tagline (README / UI): "The contract becomes tests. Passing work gets paid."

Proof-Pay is a web app for paying freelancers for website work.

  - A client writes a brief in plain language.
  - AI turns the brief into measurable acceptance checks, and both sides approve them.
  - The client authorizes the payment through PayPal (an authorization, not escrow).
  - The freelancer submits the live website URL.
  - A sandboxed browser tests the site against the agreed checks.
  - If every check passes and the client clicks Accept, PayPal captures the payment.

Scope:
  - Website deliverables only.
  - PayPal sandbox only. There are no real accounts and no production payments.
  - It was built as a hackathon project. The licence is MIT.


2. CORE DESIGN RULE
-------------------
"AI writes, explores and explains. Deterministic code decides what passed and what gets
paid."

In the code this means:
  - The AI never changes milestone state. It only returns data, and services validate that
    data with Zod.
  - Pass or fail comes only from the evaluator (api/src/checks/evaluator.ts). It uses
    measurements and evidence, never what the AI says.
  - Money moves only through paymentService.ts, and only after PayPal confirms the result.
  - Every AI workflow has a deterministic fallback, so the app works with no LLM at all.

5. ARCHITECTURE
---------------
  Browser (React SPA)
     │  cookie session (pp_sid)
     ▼
  Express API  ─────────────────────────────────────────────────────────────
     ├─ milestoneService.transition()  the ONLY way to change milestone state
     ├─ agreementService               canonical JSON, SHA-256, version-checked approvals
     ├─ paymentService ─► paypal.ts    the ONLY module holding PayPal credentials
     ├─ AI engine (runAI/callModel)    clarify, propose, fix coach, acceptance-agent steps
     ├─ verificationService            sends jobs to the worker, runs the evaluator
     ├─ jobs/loop.ts                   background ticks (queue, reconcile, reauth, deadlines)
     └─ SQLite file + artifacts/ folder (screenshots, traces, console.json)
     │
     │  POST /jobs  (Bearer WORKER_JOB_SECRET)
     ▼
  Worker (Playwright)  holds NO PayPal or LLM keys
     ├─ URL guard, DNS check, pinned resolver, per-request route checks
     ├─ asks the API for each agent step   → POST {API}/internal/agent/step (per-run token)
     ├─ streams a live trace                → POST {API}/internal/agent/trace
     └─ reads the inbox                     → GET  {API}/internal/inbox
     │
     ▼
  Deliverable website (e.g. demo site). Its contact form POSTs to the public
  {API}/inbox/:token, which the verifier then reads as evidence.

In production the API also serves the built React app (web/dist) with an SPA fallback.
The UI and API therefore share one origin.


6. THE END-TO-END PIPELINE, STEP BY STEP
----------------------------------------
There are three fixed demo users, picked in the header: client "Dana", freelancer "Ravi"
and an admin. They log in with an optional DEMO_LOGIN_CODE.

Step 0. Create project (client)
  - The New project page sends POST /api/projects with title, brief, amount (max 10000 USD)
    and deadline (1–25 days).
  - This creates a project and one milestone in state DRAFT. The milestone gets a random
    inbox_token.
  - The payee email is PAYPAL_PAYEE_EMAIL (default "freelancer@example.com").
  - The 25-day maximum exists because PayPal authorizations live 29 days.

Step 1. Clarify the brief (client, state DRAFT)
  - The client clicks "Find the vague parts", which calls POST /clarify.
  - The AI finds vague terms ("fast", "mobile-friendly", "working form", "modern", ...) and
    asks up to 6 questions, offering options where it can.
  - Fallback: a fixed dictionary of vague words (templateQuestions).
  - The client picks an option or types their own answer for each question.

Step 2. Propose the checklist (client)
  - POST /propose. The AI proposes:
      - automated checks, using ONLY the 5 catalog types
      - manual criteria (the only grounds on which the client may later reject)
      - advisory notes (informational only)
  - Zod (ProposalSchema) validates the result strictly. Fallback: templateProposal.
  - The milestone moves to PROPOSED.

Step 3. Agree and lock (client + freelancer, state PROPOSED)
  - Either party may edit the criteria as JSON. Any edit creates a new version and clears
    both approvals.
  - Each party approves a specific version number.
  - The second approval does three things in ONE database transaction:
      1. LOCK the milestone.
      2. Store the SHA-256 hash of the canonical agreement JSON.
      3. Queue the PayPal create_order operation.
  - The milestone moves to LOCKED, and the backend creates the PayPal order immediately.

Step 4. Fund / authorize (client, state LOCKED)
  - The PayPal JS SDK button (intent "authorize") opens the PayPal popup.
  - The order carries custom_id = agreement hash and invoice_id = milestone id.
  - After the buyer approves, POST /authorize authorizes the order and records the
    authorization.
  - The milestone moves to FUNDED.
  - With FAKE_PAYPAL=1, a single button approves the order in the local stand-in instead.

Step 5. Submit (freelancer, state FUNDED or FAILED)
  - The freelancer submits an https URL on an allowlisted host. The demo-site chips add the
    milestone's ?inbox= URL automatically.
  - The milestone moves to VERIFYING.

Step 6. Verify (system)
  - The job loop picks up the submission (one run at a time), creates a run and a per-run
    job token, and POSTs the job to the worker.
  - The worker opens Chromium and runs every check:
      - viewport_render
      - element_present
      - text_present
      - form_submits (AI acceptance agent, or the deterministic plan)
      - no_console_errors
  - The worker returns measurements, screenshots, traces and the console log.
  - The API saves the artifacts, waits up to 10 s for inbox rows, then evaluates each check
    deterministically.
  - Outcomes:
      - any check failed             → FAILED, and the fix coach explains each failure
      - every check passed           → REVIEW
      - only infrastructure errors   → back to FUNDED, or to FAILED if the previous finished
                                       run failed. An error never counts against the
                                       freelancer.

Step 7. Fix loop (freelancer, state FAILED)
  - The UI shows each failed check: expected value, measured value, evidence screenshots,
    agent trace, and the fix coach's explanation, reproduction steps and likely fix.
  - The freelancer fixes the site and resubmits (back to Step 5).

Step 8. Review (client, state REVIEW)
  - Accept: the milestone moves to CAPTURE_PENDING and the backend captures the payment.
    It moves to CAPTURED only when PayPal reports the capture COMPLETED.
  - Reject: allowed only by citing a manual criterion, with a reason and a note or a
    screenshot. The milestone moves to DISPUTE.

Step 9. Dispute (admin, state DISPUTE)
  - Resolve for the freelancer → CAPTURE_PENDING → capture.
  - Resolve for the client     → VOID_PENDING → void.

Step 10. Report
  - The /m/:id/report page shows:
      - PayPal's capture id and status
      - the locked agreement and its hash
      - evidence from the latest finished run
      - every run
      - PayPal operations with their idempotency keys
      - authorizations
      - the full event timeline
  - It has a Print / PDF button.

Side paths:
  - Cancel (client, FUNDED or FAILED) → VOID_PENDING → void.
  - Deadline passed (job, FUNDED or FAILED) → VOID_PENDING → void.
  - Authorization expired or reauthorization failed → AUTH_EXPIRED. The client re-authorizes:
    the milestone goes to REVIEW if a passing run exists, otherwise to FUNDED.
  - Capture declined or pre-capture mismatch → CAPTURE_FAILED. The client re-authorizes,
    which leads to CAPTURE_PENDING and an immediate capture retry.
  - Admin close (CAPTURE_FAILED or AUTH_EXPIRED) → VOID_PENDING if a live authorization
    exists, otherwise VOIDED.


7. MILESTONE STATE MACHINE (api/src/domain/milestoneState.ts)
-------------------------------------------------------------
There are 14 states:
  DRAFT, PROPOSED, LOCKED, FUNDED, VERIFYING, FAILED, REVIEW, DISPUTE, CAPTURE_PENDING,
  CAPTURED, CAPTURE_FAILED, AUTH_EXPIRED, VOID_PENDING, VOIDED.

There are 7 actors: client, freelancer, admin, system, payment, verification, job.

Events, written as from → to [allowed actors]:
  PROPOSAL_READY          DRAFT, PROPOSED → PROPOSED                          [system]
  CRITERION_EDITED        PROPOSED → PROPOSED                                 [client, freelancer]
  LOCK                    PROPOSED → LOCKED                                   [client, freelancer]
  AUTHORIZED              LOCKED → FUNDED
                          CAPTURE_FAILED → CAPTURE_PENDING
                          AUTH_EXPIRED → REVIEW if a passing run exists, else FUNDED
                                                                              [payment]
  SUBMIT                  FUNDED, FAILED → VERIFYING                          [freelancer]
  RUN_FAILED              VERIFYING → FAILED                                  [verification]
  RUN_PASSED              VERIFYING → REVIEW                                  [verification]
  RUN_ERROR               VERIFYING → FAILED if the last finished run failed, else FUNDED
                                                                              [verification]
  ACCEPT                  REVIEW → CAPTURE_PENDING                            [client]
  REJECT                  REVIEW → DISPUTE                                    [client]
  RESOLVE_FOR_FREELANCER  DISPUTE → CAPTURE_PENDING                           [admin]
  RESOLVE_FOR_CLIENT      DISPUTE → VOID_PENDING                              [admin]
  CANCEL                  FUNDED, FAILED → VOID_PENDING                       [client]
  DEADLINE_PASSED         FUNDED, FAILED → VOID_PENDING                       [job]
  AUTH_EXPIRED            FUNDED, FAILED, REVIEW, DISPUTE → AUTH_EXPIRED      [payment]
  CAPTURE_COMPLETED       CAPTURE_PENDING → CAPTURED                          [payment]
  CAPTURE_DECLINED        CAPTURE_PENDING → CAPTURE_FAILED                    [payment]
  ADMIN_CLOSE             CAPTURE_FAILED, AUTH_EXPIRED → VOID_PENDING if a live
                          authorization exists, else VOIDED                   [admin]
  VOID_CONFIRMED          VOID_PENDING → VOIDED                               [payment]

How transition() works (milestoneService.ts). Everything runs inside one IMMEDIATE SQLite
transaction:
  1. Check the actor. A wrong actor gets 403.
  2. Check the from-state. A wrong state gets 409.
  3. UPDATE milestones SET state=? WHERE id=? AND state=? and require exactly 1 changed row
     (compare-and-set). Otherwise 409 "state changed concurrently".
  4. Run the optional effect in the same transaction.
  5. Append a "transition" event.


8. DATA MODEL (api/src/db/schema.sql)
-------------------------------------
There are 10 tables:
  projects            id, title, brief, client_id, freelancer_id, freelancer_email,
                      created_at
  milestones          id, project_id, title, amount_cents, currency (USD), state,
                      deadline_at, review_window_hours, inbox_token (UNIQUE)
  agreements          milestone_id (PK), version, body_json, hash, client_approved_at,
                      freelancer_approved_at, locked_at
  authorizations      id, milestone_id, order_id, status, expires_at, replaced_by,
                      created_at
  payment_operations  id, milestone_id, type, idempotency_key (UNIQUE), status,
                      requested_at, responded_at, paypal_ref, error, target_ref
                        type:   create_order | authorize | reauthorize | capture | void
                        status: PENDING | SUCCEEDED | FAILED | UNKNOWN
  submissions         id, milestone_id, url, submitted_at
  verification_runs   id, submission_id, status (running | finished | error),
                      runner_version, started_at, finished_at, error
  check_results       id, run_id, check_id, status (passed | failed | error),
                      expected_json, measured_json, evidence_json, explanation, agent_json
  events              id (autoincrement), milestone_id, at, actor, type, data_json
  form_inbox          id (autoincrement), inbox_token, run_id, received_at, body_json

Triggers events_no_update and events_no_delete RAISE(ABORT), so the events table is
append-only (an audit log).

Database file: DB_FILE, default <repo>/data/proofpay.db.
Artifacts folder: ARTIFACTS_DIR, default <repo>/artifacts/<runId>/.


9. AGREEMENT, HASHING AND LOCKING (services/agreementService.ts)
---------------------------------------------------------------
Agreement body:
  milestoneId, checks[], manual[], advisory[], amount {value, currency}, payee {email},
  deadlineAt, reviewRule {rejectionOnlyCitingManual: true, manualCriteria: n,
  reviewWindowHours}

Canonical JSON:
  - Keys are sorted recursively.
  - There is no whitespace.
  - Keys whose value is undefined are dropped.
  - Hash = SHA-256 (hex) of that string.

Rules:
  - Writing a new proposal or edit increments the version and clears both approvals. It is
    not allowed once the agreement is locked.
  - An edit must quote the current baseVersion. Otherwise 409.
  - An approval must quote the current version. Otherwise 409.
  - The second approval runs LOCK, stores the hash and locked_at, and queues create_order,
    all in one transaction.
  - verifiedLockedAgreement() recomputes the hash before every use (order creation,
    verification, capture checks). A mismatch returns 500, which detects tampering with the
    stored row.


10. CHECK CATALOG AND DETERMINISTIC EVALUATOR (api/src/checks)
--------------------------------------------------------------
Exactly five check types (strict Zod discriminated union; no extra keys allowed):
  viewport_render    params {width: int 240..2560}
                     Pass: the page loaded and scrollWidth <= clientWidth (no sideways
                     scroll).
  element_present    params {role: one of 12 ARIA roles, name: 1..100 chars}
                     Pass: an element with that role and accessible name is visible.
                     Roles: button, link, heading, textbox, img, navigation, form, checkbox,
                     combobox, main, banner, contentinfo.
  text_present       params {text: 1..200 chars}
                     Pass: the body text contains it (whitespace normalised).
  form_submits       params {fields: 1..8 names}
                     Pass: an inbox row received between (submittedAt − 1 s) and
                     (submittedAt + 10 s) contains EVERY field's fixed test value.
  no_console_errors  params {allowList: up to 20 strings}
                     Pass: no console.error or page error remains after the allow-list
                     substrings are filtered out.

Proposal limits:
  - checks: 1 to 12
  - manual criteria: up to 6
  - advisory notes: up to 6
  - All ids must be unique and match /^[a-z][a-z0-9_-]{0,31}$/i.

Fixed test values (reproducible runs):
  name "Test User", email "test@proofpay.dev", message "Proof-Pay test message",
  phone "+1 555 0100", subject "Proof-Pay test subject", company "Proof-Pay Test Co".
  Any other field gets "Proof-Pay test <field>".

Evaluator rules:
  - No result from the worker → error.
  - An infrastructure error → error.
  - Any evidence ref that does not resolve to an artifact or inbox row of THIS run → error.
  - "passed" with no evidence at all → error.
  - Agent observations never change the verdict. Observations with unresolvable evidence
    refs are dropped and counted.

Fallback proposal (templateProposal), used when the AI is not available or its output is
invalid:
  - viewport 375 and viewport 1280.
  - If the brief mentions a form, contact, enquiry or message: a "Send" button check and a
    form_submits check on name, email and message.
  - no_console_errors.
  - Manual criterion m1: "Uses the logo and brand colours the client supplied".
  - Advisory note: "Visual polish and brand fit".

URL policy on submit (urlPolicy.ts):
  - https only, no credentials in the URL, port 443 only.
  - The hostname must match an entry in ALLOWED_HOSTS exactly (no suffix matching).
  - DEV_LOCAL_ORIGINS bypasses these rules. It is meant for local development only.


11. AI COMPONENTS (api/src/ai)
------------------------------
engine.ts: shared engine
  - runAI(): forces the model to call a "respond" tool, validates the tool input with Zod,
    retries ONCE with the validation errors on invalid output, then uses the deterministic
    fallback.
  - Every model call is logged as a model_call or model_error event. Fallbacks are logged as
    ai_fallback, and invalid output as ai_invalid_output.
  - Providers:
      - Gemini Interactions API (default): POST /v1beta/interactions with a step list and
        store:false. Thought steps are sent back with function calls.
      - Gemini generateContent (LLM_GEMINI_API=generatecontent): uses thoughtSignature. If
        parametersJsonSchema is rejected, it retries with an OpenAPI schema subset.
      - Anthropic Messages API (LLM_PROVIDER=anthropic). Default model claude-sonnet-5-5,
        or LLM_MODEL.
  - Model fallback list: LLM_MODEL, comma-separated. Default:
    gemini-3.5-flash-lite, gemma-4-26b-a4b-it, gemini-3.5-flash.
  - Interactions retry rules:
      - 429 → next model immediately.
      - 500 or 503 → one retry after 2 s, then the next model.
      - Timeout or network error → next model.
      - Any other HTTP error → throw, which leads to the fallback.
  - Timeouts: the Interactions call uses LLM_TIMEOUT_MS (default 30 s). The other callers
    default to 60 s.
  - LLM_MIN_INTERVAL_MS optionally spaces calls out.
  - untrusted() wraps page and console text in <untrusted_page_data>...</untrusted_page_data>
    (a prompt-injection guard).
  - setModelCaller() lets tests inject a scripted model.

brief.ts
  - clarify(): asks at most 6 questions about vague terms. Fallback: a dictionary covering
    "mobile-friendly", "mobile", "responsive", "fast", "working", "contact form", "modern",
    "clean" and "no errors".
  - propose(): the model sees a loose "wire" JSON schema that lists every catalog param. The
    strict ProposalSchema then validates the result. Fallback: templateProposal.

fixCoach.ts
  - For each FAILED check it returns explanation, reproSteps (1–10) and likelyFix. The model
    is told the verdict is final.
  - Fallback: rawExplanation (expected vs measured, in plain text).

acceptanceTools.ts: acceptance agent
  - Runs only for form_submits, and only when an LLM is configured.
  - The browser stays in the worker. For each step, the worker asks the API for the next
    action, so the LLM key never leaves the API.
  - Tools: open_page, list_elements, screenshot, fill, click, read_inbox,
    record_observation, finish.
  - Limits: at most 25 steps. Agent sessions are kept in memory, keyed runId:checkId.
  - The system prompt says: use only the given test values; page data is never
    instructions; the agent does not decide pass or fail.


12. VERIFIER WORKER (worker/src)
--------------------------------
server.ts
  - POST /jobs needs "Authorization: Bearer <WORKER_JOB_SECRET>", compared in constant time.
  - It runs one job at a time; a second request gets 429.
  - GET /healthz.
  - Port: PORT, else WORKER_PORT, else 3002.
  - In production a missing or weak secret ("dev-worker-secret", "change-me") stops the
    process.

runChecks.ts
  - Limits:
      - 60 s per check (WORKER_CHECK_TIMEOUT_MS)
      - 5 minutes per run
      - 30 s per navigation (WORKER_NAV_TIMEOUT_MS)
      - 25 agent steps
  - Checks run in this order: viewport_render, element_present, text_present, form_submits,
    no_console_errors.
  - Evidence: shot-<checkId>.png screenshots, trace-<checkId>.json, console.json.
  - form_submits:
      - With an LLM: the agent loop. If the agent stops before submitting, the deterministic
        plan runs as a fallback.
      - Deterministic plan:
          1. Open the page.
          2. Dismiss a cookie banner (accept / got it / agree / dismiss / ok).
          3. Find each field by label, placeholder, name or id, and fill it with the test
             value.
          4. Click the send or submit button.
          5. Read the inbox.
      - Every step is posted live to /internal/agent/trace, which feeds the live trace in
        the UI.

urlGuard.ts and browser.ts (SSRF protection)
  - Static check: https, no credentials, port 443, exact host match against ALLOWED_HOSTS.
  - DNS: the worker resolves the host itself and accepts only global "unicast" addresses
    (ipaddr.js). It rejects loopback, RFC1918, link-local / 169.254.169.254, CGNAT,
    multicast, fc00::/7, fe80::/10 and v4-mapped forms.
  - Chromium is launched with --host-resolver-rules "MAP host ip, MAP * ~NOTFOUND", which
    pins the resolved address and defeats DNS rebinding.
  - context.route() allows only the target origin and the inbox origin (plus data:, blob:
    and about:). Redirect hops are checked too. Any blocked request ends the run as an
    error.
  - Service workers and downloads are blocked. Locale is en-US and timezone is UTC.


13. PAYMENTS (api/src/services/paypal.ts, paymentService.ts)
------------------------------------------------------------
PayPal APIs used:
  OAuth2      /v1/oauth2/token (client credentials, cached until 60 s before expiry)
  Orders v2   create (intent AUTHORIZE), get, authorize
  Payments v2 capture (final_capture: true), void, reauthorize
  JS SDK      @paypal/react-paypal-js, intent "authorize", with the CSP nonce passed in

The order carries:
  custom_id        the agreement hash
  invoice_id       the milestone id; "<milestoneId>-<attempt>" from the second attempt on
  reference_id     same as invoice_id
  payee            payee email, only when PAYPAL_PAYEE_MODE=override
  payer            pre-filled buyer email, only when PAYPAL_PREFILL_BUYER_EMAIL is set
                   (demo convenience)
  amount, description

Idempotency:
  - Every write first creates a payment_operations row whose key is
    <milestoneId>:<type>:<attempt>. The key is sent as PayPal-Request-Id and reused on every
    retry.
  - An open PENDING or UNKNOWN operation for the same target is reused.
  - An in-memory "inflight" set stops the same operation from running twice at once.
  - A 4xx response is definitive (FAILED). A timeout, network error or 5xx is UNKNOWN and
    left to the reconciler.

ensureOrder():
  - Reuses the last order if it is not yet authorized and PayPal still has it.
  - Creates a new order (next attempt) if PayPal definitively reports the old one gone (404)
    or VOIDED.

authorize():
  - Allowed in LOCKED, AUTH_EXPIRED and CAPTURE_FAILED.
  - The order id must belong to the milestone.
  - The response ORDER_ALREADY_AUTHORIZED is reconciled through GET order.

capture() (only in CAPTURE_PENDING):
  1. GET the order. If a capture already exists, record it instead of capturing again
     (crash recovery).
  2. Pre-capture check:
       - amount and currency must match
       - custom_id must equal the hash
       - the payee email must match (in override mode, or whenever PayPal reports one)
     Any mismatch → CAPTURE_FAILED.
  3. Capture with the stable key:
       - COMPLETED → CAPTURED
       - DECLINED or FAILED → CAPTURE_FAILED
       - anything else → UNKNOWN

voidAuth() (only in VOID_PENDING):
  - Voids the authorization.
  - VOIDED is recorded only once GET order confirms VOIDED or EXPIRED.

Reconciler (startup, then every minute for operations older than 30 s):
  - Re-checks every PENDING or UNKNOWN operation against PayPal and records what PayPal
    shows.
  - If PayPal shows nothing, it retries with the SAME key, never a new one.

Reauthorization (reauthorizeDue):
  - An expired authorization → AUTH_EXPIRED.
  - After the 3-day honor period: one reauthorize attempt per original authorization.
    A definitive failure → AUTH_EXPIRED.

Fake PayPal (dev/fakePaypal.ts, FAKE_PAYPAL=1):
  - An in-process stand-in mounted at /fake-paypal.
  - It honours PayPal-Request-Id.
  - Failure knobs for tests:
      - capture: ok | decline | timeout_after_capture | server_error
      - void: ok | timeout_after_void
      - reauthorize: ok | fail
  - Helpers: approve, tamper, expire. The UI shows a banner when it is in use.


14. BACKGROUND JOBS (api/src/jobs/loop.ts)
------------------------------------------
On startup:
  - recoverStaleRuns(): runs left "running" are marked as error (RUN_ERROR).
  - reconcile().

Every 1 second:
  - processQueue(): starts the next VERIFYING submission that has no run yet (one at a time).

Every 60 seconds:
  - reconcile({minAgeMs: 30000})
  - reauthorizeJob
  - deadlinesJob: FUNDED or FAILED milestones past deadline_at → DEADLINE_PASSED → void.

Job errors are logged to the console and appended as job_error events.

18. SECURITY MEASURES
---------------------
Sessions and roles:
  - Roles come only from the server-side session store, never from request fields.
  - Session ids must be 48 hex characters, are random and expire after 12 h.
  - Cookie flags: HttpOnly, SameSite=Lax, Max-Age, and Secure when PUBLIC_BASE_URL is https.

Response headers:
  - CSP with a per-request nonce, allowing the PayPal origins and Google Fonts.
  - frame-ancestors 'none', X-Frame-Options DENY, nosniff, Referrer-Policy,
    Permissions-Policy (camera, mic and geo off), COOP same-origin-allow-popups.
  - HSTS on https.
  - x-powered-by is disabled.

Rate limits (in memory):
  - login: 20 per minute per IP
  - AI and submit routes: 12 per minute per session
  - TRUST_PROXY sets Express "trust proxy".

Other controls:
  - Job tokens and the login code are compared in constant time.
  - The worker has no PayPal or LLM secrets.
  - SSRF protections in the worker (section 12).
  - The public inbox accepts posts only during a run, with a per-run cap.
  - Artifact file names are restricted to ^[a-z0-9][a-z0-9._-]*$.
  - /artifacts requires a login.
  - Reject screenshots must be inline raster data URLs.
  - SQL uses prepared statements. The single interpolated column name comes from two fixed
    values.
  - Containers run as non-root ("node" for the API, "pwuser" for the worker).

24. KNOWN GAPS, LIMITATIONS AND OBSERVATIONS
--------------------------------------------
Listed in the README:
  - Reauthorization needs an authorization older than 3 days, so it has only been tested
    against the fake PayPal.
  - Not implemented: auto-capture, Payouts, the disputes API, API deliverables,
    Lighthouse / axe checks, design-quality judging.
  - Network-level egress restriction for the worker must come from the host (firewall or
    egress proxy). Compose and the app cannot enforce it.

Visible in the code:
  - Authorization is by role only. There are three fixed demo users, and any logged-in role
    can list and open every milestone (no per-object ownership check).
  - The following live in the memory of a single process and are lost on restart:
    sessions, rate-limit counters, agent sessions, job tokens and the payment "inflight"
    set.
  - The verification queue processes one run at a time, and the worker accepts one job at a
    time.
  - Only USD is used (the currency is fixed when a project is created).
  - DEV_LOCAL_ORIGINS and PAYPAL_PREFILL_BUYER_EMAIL are for development or demos, and the
    README says to clear them for a public deployment.
  - On Render, the static demo service publishes the whole demo-sites folder, so serve.mjs
    is also reachable as a static file. It contains no secrets.
  - web/src/api.ts's Config type does not declare allowedHosts. Submit.tsx reads it through
    an "as any" cast.

About proofpay.txt (the earlier analysis file, left unchanged):
  - "Nothing has been committed to git yet" is out of date: there are now 5 commits on
    origin/main.
  - It says the Dockerfiles have never been built. That was not re-checked in this session,
    and Render will build Dockerfile.worker.
  - It predates render.yaml and the worker PORT change.
